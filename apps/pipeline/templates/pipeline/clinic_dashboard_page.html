{% extends "base.html" %} {% load i18n humanize %} {% comment %} Clinic dashboard — totals across a reader-chosen range (Plan 16, task 16.3). Every figure comes from `stats`, an apps.pipeline.dashboard.DashboardStats built live in ClinicDashboardPage.get_context from DailyAggregate rows — never from a stored field on this page, which has none (D1). No AI-written prose anywhere on this page (D12). No JavaScript, by construction rather than as a fallback (D9): the presets are plain links carrying the range in the query string, and the From/To form is a GET form with a visible Apply submit. Nothing here auto-submits, so nothing here needs a script. The chart is server-rendered SVG for the same reason (D2) — see apps.pipeline.footfall_chart, whose geometry this shares with the reports index, styled through its own `dash-chart` block rather than that page's `ri-funding-mix` one. `pct` deliberately means two things, following DashboardStats' docstring: share of total_visits in funding_rows/age_bands, but share of the larger of Female/Male in gender_rows — which is why the Gender card renders no "%" text at all, only bars scaled to each other. Zakat% + Regular% can sum to under 100 when a range holds unknown-payment visits; that shortfall is left implicit and the counts beside every bar stay authoritative (D5). Revenue surfaces (the 4th KPI card, the "Revenue by service" table and the side-column layout switch) are written against `has_revenue` and are inert today — `dashboard.has_revenue` returns False until the clinic software ships fee columns (D6/D13), so Phase 2 lights them up with no template work. All colour is from semantic tokens (tokens.css); component styles live in static/css/dashboard.css. `dash` is the page-scoped root class. {% endcomment %} {% block content %}
