# Plan 11, Track E — E1/E2 research (options review, no build)

**Status:** research/options doc per Stage 4 ("supporting docs" category) — a
short-lived write-up, not a task file. Produced by the "E1 + E2 research"
session named in Plan 11's status note (2026-07-23). No code changed, no

## E1 — design sketch: an update-routing skill

### What already exists to build on

- **Content lives in Wagtail, not git.** `apps/core/models.py` and
  `apps/pipeline/models.py` define the page tree (`HomePage`, `AboutPage`,
  `DonatePage`, `NewsletterPage`, `DailyReportPage`, `DonorsPartnersPage`,
  etc.). Editing a page's copy/fields is a database write via the Wagtail
  admin or the ORM — it is never a file in the repo, so it never goes through
  a git branch or PR.
- **The repo already has a "draft, never publish" write path for automated
  *content*.** `apps/pipeline/newsletter_drafting.py` (Plan 09) is the
  precedent, but the rule is narrower than "never calls `.publish()`"
  (corrected 2026-07-23, found by code-review-tc: that module *does* call
  `.publish()`, at line 75). The actual split is by what's being published:
  the newsletter **content page itself** only ever gets `page.save_revision()`
  (line 172) — the module docstring's "AI/automation code holds no publish
  permission" is scoped to that content, not to every `.publish()` call in
  the module. Separately, the module auto-creates its singleton
  `NewsletterIndexPage` structural container the first time it's needed and
  publishes *that* immediately (line 75) — an empty index page has nothing
  editorial in it to review, so there's nothing invariant #4 protects there.
  `apps/pipeline/report_publishing.py` mirrors the exact same split: its
  singleton `ReportIndexPage`/`CampReportIndexPage` containers get
  auto-published on first creation, while the actual `DailyReportPage`
  content follows its own narrower rule (CLAUDE.md invariant #4's Plan 08
  exception for the daily numbers+sentence; Plan 11 B8/B9's free-text
  summary/flag stay draft-only pending human approval). `seed_core_content.py`
  /`seed_initial_content.py` are a third instance of the same
  structural-container pattern, for first-run seeding. **E1 takeaway:**
  "never `.publish()` from automation" is the rule for actual editorial
  content; auto-creating an empty structural container and publishing it
  immediately is a distinct, already-established pattern, not an exception to
  track separately.
- **Code changes already have a full, working pipeline.** Branch →
  implement, mirroring named precedent → tests + lint → `code-review-tc`
  loop until clean → `gh pr create --draft` (CLAUDE.md "Workflow
  conventions"; lifecycle Stages 8–9).
- **Publishing (in either sense) already has its own gated skill/flow.**
  `release-prod` ships *code* to production and is explicit that it does
  **not** touch content publishing — that stays Wagtail's in-app
  draft → preview → publish click, gated on a human (CLAUDE.md invariant
  #4). `release-prod`'s "never deploy without an explicit yes" pattern is the
  right model to copy for any content-publish action too.

So the three destinations E1 needs to route into are not new — a code-change
pipeline, a draft-only content-write path, and a human-gated publish step all
already exist independently. E1's job is purely classification and handoff,
not new machinery.

### Routing logic sketch

A repo-local skill, e.g. `.claude/skills/route-change-request/SKILL.md`,
invoked when the maintainer states a plain-English change request (typed
directly into a Claude Code session today; a future WhatsApp-relayed message
later, per E1's own framing — but the classifier's input is just text either
way, so building it against typed input first is the right order).

**Step 1 — gather context before classifying.** Load, in order:
1. `CLAUDE.md` (privacy invariants, stack, workflow conventions — the
   non-negotiables that constrain every branch below).
2. `.claude/plans/README.md` (the plans index) plus a grep of open items
   across `.claude/plans/*.md` — a request that matches an already-planned,
   not-yet-done item (e.g. "relabel the impact heading" ~ D2) should be
   routed *and* cross-referenced to that item rather than treated as freestanding.
3. The Wagtail page models (`apps/core/models.py`,
   `apps/pipeline/models.py`) and a targeted grep for the request's subject
   (page title, field name, template string) across `apps/*/templates` and
   `apps/*/models.py` — this is what actually decides "is this data a
   template/model or a page field", not a guess.

**Step 2 — classify into one of three routes:**

| Signal in the request | Route | Handoff |
|---|---|---|
| Names a bug, a behavior, a template/style/logic change, or anything that requires editing a `.py`/template/CSS file | **Code change** | Branch per CLAUDE.md naming convention, implement mirroring precedent, tests + lint, `code-review-tc` loop, `gh pr create --draft` (Stage 8–9 as normal — E1 does not shortcut review). |
| Names copy, a page's text/images/ordering, or "add/update an entry on page X" where X is a real Wagtail page/model field | **Wagtail draft** | A management command or script that loads the target page and calls `save_revision()` **only** — mirroring `newsletter_drafting.py`'s rule. Never `.publish()`. Leaves an editor-visible draft revision for the maintainer to review in the Wagtail admin, exactly like the monthly newsletter flow. |
| Explicitly asks to make something live — "publish the July newsletter draft" (content) or "ship this to production" / "deploy" (code) | **Publish action** | Content: tell the maintainer to review and click Publish in the Wagtail admin (or, at most, drive the publish only after an explicit in-session "yes, publish", mirroring `release-prod`'s confirm-first pattern — this is not a route E1 should take unattended). Code: hand off to the existing `release-prod` skill verbatim; it already owns every precondition and confirmation gate. |

**Step 3 — ambiguity handling.** Several real requests from Plan 11 itself
straddle the line (e.g. D2's "impact so far" figure could be a template
constant or a model field — Plan 11 lists this as an open question to trace,
not assume). When the grep in Step 1 doesn't land on a single unambiguous
file/field, the skill should say so and ask, not guess — consistent with the
lifecycle doc's "don't build on a guess" principle and this being a
low-stakes, cheap-to-ask moment (a maintainer typing a request is already in
the loop).

**Step 4 — safety rails (non-negotiable, mirrors existing conventions):**
- Never call `.publish()` on *editorial content* from an automated path —
  auto-creating an empty singleton structural container (an index page) and
  publishing it immediately is the one already-established exception to this
  (see the corrected precedent note above), not a new one E1 introduces.
  Separately, the one narrow CLAUDE.md invariant #4 exception (the
  daily-report AI summary sentence) is unrelated and stays exactly that
  narrow; E1 does not create a second content-publish exception.
- Never skip `code-review-tc` before a code-change PR is opened — same rule
  as every other branch in this repo.
- Never touch the privacy invariants list itself as a "content edit" — if a
  request's subject is `CLAUDE.md` or a privacy-relevant model, that is
  always a code-change route (so it gets full review), never a Wagtail draft.

### What this buys, concretely

Every future small site-edit request the maintainer makes (labels, copy
tweaks, a new donor entry, a bug report) gets the same "which of the three
existing workflows does this belong to" decision made consistently instead of
re-derived by hand each time — which is exactly the "real leverage" the plan
already credits E1 with. It requires no new infrastructure: no new endpoint,
no new model, no new dependency. It is a skill file plus, at most, one or two
small management-command-style helper scripts that just call
`save_revision()` on the right page — themselves following the
`draft_monthly_newsletter` precedent almost verbatim.

## E2 — options review: WhatsApp feedback ingestion

### Candidate: whatsapp-claude-plugin (rich627/whatsapp-claude-plugin)

From the repo's own description and README:

- **What it does:** a Claude Code plugin/channel that lets a user send and
  receive WhatsApp messages through a live Claude Code session — bidirectional
  chat, media, voice transcription, per-group personalities, and a
  tool-approval flow via emoji reaction.
- **Connection method:** uses **Baileys**, an *unofficial* WhatsApp Web
  library — not Meta's official Business API. It pairs as a "linked device"
  (scan a code, no developer account or API key). This is explicitly the
  unofficial-protocol path, not an approved integration; the README does not
  address WhatsApp's Terms of Service, and automating a personal account this
  way carries some ToS risk that Meta could act on (account/device
  restriction) — a risk the project doesn't disclaim.
- **Data storage:** runtime state (auth, allowlists, group config, and the
  conversation inbox itself) is kept locally in `~/.whatsapp-channel/` on
  whatever machine runs it — "no third-party servers in between," per its own
  README. That's a reasonable property in isolation, but it means the
  maintainer's personal laptop becomes the place raw WhatsApp message content
  is retained, not this Django app's already-audited data path.
- **Setup cost:** needs Bun, Node.js, FFmpeg, and (for the optional voice
  feature) Python 3 + `mlx-whisper` targeting Apple Silicon. No Docker, which
  is a plus, but it's still a standing background process the maintainer
  would run and keep alive on their own machine — a meaningfully bigger
  footprint than anything else in this stack's personal-laptop workflow.
- **Fit for the actual ask:** it's built for *live, ongoing* conversational
  use (a linked device staying paired), not for pulling the *history* already
  sitting in an existing group. It doesn't offer a "import this group's past
  messages" feature — it's the wrong shape for "feedback already sitting in a
  WhatsApp group," even though it's a good fit for E1's longer-term
  aspiration ("send a WhatsApp message to a thandkoi-clinics-assistant").

### Lighter alternatives considered

1. **Manual export + paste (zero-build baseline).** WhatsApp's built-in
   "Export chat" feature dumps a group's history to a text file (with or
   without media) that the maintainer can hand to a Claude Code session
   directly, exactly the same way this very plan was produced — Plan 11's own
   header states its source is "maintainer's Google Doc, 'Feedback' (fetched
   2026-07-22)... a point-in-time capture." A WhatsApp export slots into that
   identical pattern with zero new code, zero new dependency, and zero new
   standing process. Cost: purely manual, and doesn't stay "live" — the
   maintainer has to think to do it again.
2. **Official WhatsApp Business Platform (Meta Cloud API) webhook.**
   ToS-compliant, but requires business verification and a *separate* business
   phone number; a webhook endpoint this Django app doesn't currently have
   (new attack surface, new maintenance burden); and — critically — it only
   receives *new* messages sent to that business number going forward. It
   cannot ingest the history of an existing personal-number group chat, so it
   doesn't actually solve the stated problem either, only a future version of it.
3. **Twilio's WhatsApp API.** Same fundamental limitation as (2) — official,
   but forward-only, needs its own number, needs a webhook, needs an ongoing
   Twilio account/cost — with an extra vendor and billing relationship on top.

### Privacy: does WhatsApp content risk PHI?

Yes, and this is a materially different risk profile than Track B's B8/B9
resolution. B8/B9 were unblocked because the maintainer confirmed the clinic
software's data-entry UI *structurally* cannot accept PII into those specific
free-text columns — a guarantee about a controlled form, not an assumption
about free text in general. A WhatsApp group has no such structural
guarantee: it is unstructured human conversation, and there is a real,
non-hypothetical chance a family member or clinic staffer discusses a
specific patient by name in a coordination/feedback group. CLAUDE.md
invariant #2 ("never send patient data to any AI model") would apply in full
force the moment group content is fed to Claude — whether via the plugin's
live message routing or via a manual paste-into-session — and unlike the
upload pipeline, there is no in-memory-aggregate-then-discard step available
for free-text chat. Any ingestion route (automated or manual) needs a human
read/redact pass before content reaches a model call; it cannot inherit
B8/B9's "structurally safe by construction" reasoning by analogy.

### Weighing it

| | whatsapp-claude-plugin | Manual export/paste | Official Business API / Twilio |
|---|---|---|---|
| Setup cost | Real (Bun/Node/FFmpeg/mlx-whisper, linked-device pairing) | None | Real (business verification, webhook endpoint, vendor account) |
| Ongoing maintenance | A standing local process to keep paired/alive | None | Token refresh, webhook uptime, billing |
| Privacy surface | Broadest — live inbox retained on-machine, unofficial protocol | Narrowest — maintainer controls exactly what's exported/pasted, same as the existing Google-Doc pattern | Forward-only, but still routes content through a third party (Meta/Twilio) plus a new webhook surface in this app |
| Solves "history already in the group"? | No (live-session tool, not a history importer) | Yes (export includes full history) | No (forward-only) |
| ToS risk | Real, undisclaimed in the README | None | None |

Manual export/paste is the only option of the three that both solves the
stated problem (existing history) and adds no new privacy surface or ToS
risk — and it's already the exact pattern this repo used to produce Plan 11
itself.

## Recommendation

**Build E1 now.** It's small, fully grounded in precedent that already
exists in this repo (`newsletter_drafting.py`'s save-revision-only rule,
`code-review-tc`, `release-prod`), needs no new infrastructure, and pays off
on every future small site-edit request — matching the plan's own existing
lean ("E1 has real leverage... but is itself a small design exercise before
it's a task file").

**Confirm the defer on E2, with one refinement.** The plan's parked note
("revisit once E1 exists") is right to defer a *build* — but this review's
finding is that even after E1 exists, `whatsapp-claude-plugin` specifically
should not be the default answer. Its privacy surface (unofficial protocol,
locally-retained live inbox, no structural PHI guarantee for free-text group
chat) and setup/maintenance cost are disproportionate to what's actually
needed, and it doesn't even solve the stated problem (importing existing
group history) — it's built for live sessions, not history import. The
durable, near-zero-cost answer for "feedback already sitting in a WhatsApp
group" is the same manual export-and-paste pattern this repo already used to
produce Plan 11 from the maintainer's Google Doc — no new plan needed to do
that today, whenever there's a next batch of group feedback to triage. Revisit
a built (automated) ingestion path only if manual export becomes a recurring,
real pain point — not speculatively, and not via the unofficial-protocol
plugin without weighing an official API path's forward-only limitation
against it again at that time.
